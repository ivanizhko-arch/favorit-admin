# Жалобы: что сделать в основном сервисе и приложении

Документ для тех, кто ведёт `favorit-app` и мобильное приложение.
Админ-сервис уже готов и ждёт вызовов.

Политика подачи и её обоснование — в [research-complaints.md](research-complaints.md).

## Как это устроено

Клиент подаёт жалобу в приложении → приложение зовёт основной backend →
**основной backend передаёт жалобу админ-сервису** → админ-сервис проверяет
правила, сохраняет и ставит задачу отделу контроля качества.

**Почему не писать в базу напрямую.** Правила подачи (одна открытая жалоба
на тему, паузы, лимиты) — это логика, а не хранение. Если бы основной сервис
писал в таблицу сам, правила пришлось бы продублировать там, и две копии
политики неизбежно разъехались бы уже на первой правке. Плюс проверка и
вставка должны быть атомарными, иначе два быстрых нажатия создадут два дубля.

Один HTTP-вызов внутри той же машины — небольшая цена за единственный
источник правды.

## Эндпоинты админ-сервиса

Базовый адрес: `http://127.0.0.1:8001`. Оба требуют заголовок
`X-Internal-Token` со значением `INTERNAL_API_TOKEN` из `.env` админ-сервиса.

### Получить список тем и ограничения

```
GET /admin/internal/complaints/categories
X-Internal-Token: <токен>
```

```json
{
  "categories": [
    {"code": "manager",   "label": "Работа менеджера"},
    {"code": "deadlines", "label": "Сроки по делу"},
    {"code": "money",     "label": "Деньги и платежи"},
    {"code": "app",       "label": "Мобильное приложение"},
    {"code": "other",     "label": "Другое"}
  ],
  "answer_days": 10, "text_min": 10, "text_max": 4000
}
```

Приложение должно строить форму по этому ответу, а не хардкодить темы: иначе
при добавлении темы придётся выпускать новую версию приложения.

### Подать жалобу

```
POST /admin/internal/complaints
X-Internal-Token: <токен>
Content-Type: application/json

{"email": "client@example.com", "category": "manager", "text": "..."}
```

**201** — принята:

```json
{"id": 42, "answer_due": "2026-08-09T12:00:00+00:00", "answer_days": 10}
```

**409** — подавать сейчас нельзя:

```json
{"detail": {"message": "Ваша жалоба по этой теме от 12 июля ещё в работе. Мы ответим до 22 июля...",
            "reason": "duplicate_category"}}
```

`message` написан для клиента — покажите его в приложении **как есть**, не
заменяя своим текстом. Он объясняет причину и что делать дальше; из-за этого
у человека пропадает желание отправить дубль.

Коды `reason`: `duplicate_category`, `cooldown`, `day_limit`, `month_limit`,
`bad_category`, `text_too_short`, `text_too_long`, `no_email`.

**403** — неверный токен. **503** — токен не настроен на стороне админки.

## Правка в основном сервисе

```python
COMPLAINTS_URL = "http://127.0.0.1:8001/admin/internal/complaints"

@router.post("/api/complaints")
def submit_complaint(body: ComplaintIn, email: str = Depends(get_current_user)):
    """Проксируем в админ-сервис: там живут правила подачи и хранение."""
    try:
        r = httpx.post(
            COMPLAINTS_URL,
            headers={"X-Internal-Token": settings.internal_api_token},
            json={"email": email, "category": body.category, "text": body.text},
            timeout=10,
        )
    except httpx.HTTPError:
        raise HTTPException(status_code=503,
                            detail="Не удалось отправить жалобу, попробуйте позже")
    if r.status_code == 201:
        return r.json()
    if r.status_code == 409:
        # Причина отказа предназначена клиенту — отдаём как есть.
        raise HTTPException(status_code=409, detail=r.json()["detail"]["message"])
    raise HTTPException(status_code=503,
                        detail="Не удалось отправить жалобу, попробуйте позже")
```

`e-mail берём из токена авторизации`, а не из тела запроса. Иначе клиент
сможет подать жалобу от чужого имени и заодно обойти лимиты.

Добавьте `INTERNAL_API_TOKEN` в `.env` основного сервиса — то же значение,
что и в админке.

## Что нужно в приложении

- Экран подачи: выбор темы из списка с сервера, поле текста с подсказкой
  о минимальной длине, кнопка отправки.
- После успеха показать: «Жалоба принята. Ответим до <дата>». Срок берётся
  из ответа, не зашивайте 10 дней в приложение.
- При 409 показать `message` с сервера без изменений.
- **Экран «Мои жалобы» со статусами.** Не украшение: клиент отправляет
  повторную жалобу именно тогда, когда не видит, что с первой. Без этого
  экрана правило «одна открытая на тему» будет выглядеть как поломка.
- Вложения на первом этапе не делаем — отдельная работа с хранилищем.

## Безопасность

**Nginx не должен пускать `/admin/internal/*` снаружи.** Сейчас он проксирует
`/admin/*` целиком, значит служебные эндпоинты окажутся в интернете под
защитой одного лишь токена. Добавьте до общего правила:

```nginx
location /admin/internal/ { deny all; }
```

Основной сервис ходит на `127.0.0.1:8001` напрямую, мимо nginx, поэтому
запрет ему не мешает.

Токен генерируется так же, как любой секрет:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

## Как проверить

```bash
TOKEN=$(grep '^INTERNAL_API_TOKEN=' .env | cut -d= -f2)
curl -s -X POST http://127.0.0.1:8001/admin/internal/complaints \
  -H "X-Internal-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"test@example.com","category":"other","text":"Проверка связи, тестовая жалоба"}'
```

Ожидаем 201 с датой ответа. Повторный тот же запрос должен дать 409 с
человеческим объяснением. Дальше:

```bash
.venv/bin/python scripts/nps_worker.py
```

В Битриксе появится задача на отдел контроля качества, в админке на вкладке
«Качество» — строка в разделе «Жалобы».

Проверьте, что снаружи служебный эндпоинт закрыт:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  https://app.favorit-consult.ru/admin/internal/complaints/categories
```

Ожидаем 403 от nginx, а не ответ сервиса.
