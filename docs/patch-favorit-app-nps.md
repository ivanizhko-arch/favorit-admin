# Патч для основного backend: сохранять все оценки 0-10

Документ для того, кто ведёт репозиторий `favorit-app`. Админ-сервис менять
не нужно — он уже готов и ждёт данных.

## Зачем

Сейчас оценки ниже 8 **выбрасываются до записи в базу**. В `favorit-admin/app/db.py`
это зафиксировано в схеме:

```
# NPS-оценки клиентов (0-10) после «Долги списаны».
# Сохраняем только 8-10 (промоутеры) — по требованию бизнеса.
CREATE TABLE IF NOT EXISTS nps_scores (
    ...
    score INTEGER NOT NULL,      -- 8, 9 или 10
```

Из-за этого недовольный клиент, поставивший 3, не существует ни для кого:
ни отдел контроля качества, ни руководство о нём не узнают. Задача «низкие
оценки направлять в контроль качества» без этой правки не решается ничем —
данных просто нет.

## Что поменять

Найти в `favorit-app` обработчик, принимающий оценку от приложения (эндпоинт
вида `POST /api/nps` или `/api/nps/score`) и убрать отсев по порогу.

Было примерно так:

```python
@router.post("/api/nps")
def submit_nps(body: NpsIn, email: str = Depends(get_current_user)):
    # Сохраняем только промоутеров
    if body.score < 8:
        return {"ok": True}          # <- оценка теряется здесь
    nps_id = db.save_nps_score(email, body.score)
    return {"ok": True, "id": nps_id}
```

Нужно так:

```python
@router.post("/api/nps")
def submit_nps(body: NpsIn, email: str = Depends(get_current_user)):
    # Сохраняем все оценки 0-10. Низкие разбирает отдел контроля качества
    # через админ-сервис, поэтому терять их нельзя.
    if not 0 <= body.score <= 10:
        raise HTTPException(status_code=400, detail="Оценка вне диапазона 0-10")
    nps_id = db.save_nps_score(email, body.score)
    # Экран «Оставьте отзыв на Яндекс.Картах» по-прежнему показываем только
    # довольным — просить публичный отзыв у недовольного клиента незачем.
    return {"ok": True, "id": nps_id, "ask_review": body.score >= 8}
```

Порог `ask_review` — **отдельное решение** и с рейтингом менеджеров не связан.
В админке лучшими считаются 9-10 (`QC_PROMOTER_MIN`), но просить отзыв у
поставившего 8 вполне разумно. Если захотите свести пороги — меняется только
это число.

Ключевое: **фронтовое поведение не меняется**, меняется только то, что запись
доходит до базы. Если приложение ориентируется на ответ, чтобы решить,
показывать ли предложение оставить отзыв, — отдайте это отдельным полем
(`ask_review` выше), а не фактом отсутствия записи.

## Комментарии в схеме

В `favorit-app/app/db.py` поправить два комментария, чтобы схема не врала:

```python
# NPS-оценки клиентов (0-10) после «Долги списаны».
# Храним весь диапазон: 0-6 разбирает контроль качества, 8-10 идут
# в рейтинг менеджеров.
CREATE TABLE IF NOT EXISTS nps_scores (
    ...
    score INTEGER NOT NULL,      -- 0..10
```

И в докстроке `save_nps_score` убрать «Ожидается score в 8..10».

Те же комментарии стоит синхронно поправить в `favorit-admin/app/db.py` —
файл общий по смыслу, и расхождение путает.

## Миграция не нужна

Схема таблицы уже допускает любое целое в `score`. Ни `ALTER`, ни пересоздание
не требуются. Старые записи остаются как есть — в них просто нет низких оценок,
и это нормально: рейтинг и отчёты считаются по месяцам.

## Как проверить, что всё сошлось

После деплоя правки:

```bash
# поставить тестовую низкую оценку из приложения (или curl'ом), затем:
sqlite3 favorit.db "SELECT id, email, score, created_at FROM nps_scores ORDER BY id DESC LIMIT 5"
```

Дальше на стороне админ-сервиса:

```bash
cd ~/favorit-admin
.venv/bin/python scripts/nps_worker.py
```

В выводе должно появиться `"linked": {"linked": 1, ...}` и `"tasks": {"created": 1, ...}`,
а в Битриксе — задача на отдел контроля качества. В админке строка будет
подсвечена и покажет номер задачи.

## Порядок выкатки

Правки независимы, но осмысленный порядок такой:

1. Выкатить админ-сервис (эта ветка). Он начнёт разбирать существующие
   оценки и привязывать их к менеджерам — задач при этом не создаст,
   потому что низких оценок в базе пока нет.
2. Проверить в админке раздел «Контроль качества»: рейтинг менеджеров должен
   заполниться по промоутерам.
3. Выкатить эту правку в `favorit-app`.
4. Дождаться первой низкой оценки и убедиться, что задача создалась.

Обратный порядок тоже рабочий, но тогда низкие оценки полежат в базе
неразобранными до выката админки — это не потеря, воркер подберёт их
задним числом (в пределах `QC_TASK_MAX_AGE_DAYS`, по умолчанию 7 дней).
