# Фаворит · Админ-панель

Изолированный сервис администратора. Отдельный от основного backend (`favorit-app`), работает на порту **8001**. Nginx маршрутизирует `https://app.favorit-consult.ru/admin/*` сюда, а `/api/*` — на главный сервис.

Читает и пишет ту же SQLite-базу `favorit.db`, что и главный сервис. Данные общие, код разделён.

## Локальная разработка

```bash
# Один раз:
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Отредактируй .env (пароль, путь к БД если нужно)

# Каждый раз:
source .venv/bin/activate
uvicorn app.main:app --reload --port 8001
```

Открой в браузере: **http://127.0.0.1:8001/admin**. Пароль — из `.env` (по умолчанию `admin123`).

## Двухфакторная аутентификация (2FA)

Вход в админку защищён TOTP-кодом (Google Authenticator, Яндекс.Ключ, 1Password).
Реализован на stdlib, без сторонних библиотек — см. `app/security.py`.

Включение:

```bash
python scripts/gen_totp.py          # выведет секрет и инструкцию
# добавить ADMIN_TOTP_SECRET=... в .env
python scripts/gen_totp.py --check <СЕКРЕТ>   # проверить до перезапуска
sudo systemctl restart favorit-admin
```

Пока `ADMIN_TOTP_SECRET` пуст, вход работает как раньше — только по паролю.
**На проде секрет должен быть заполнен**: админка управляет персональными данными
клиентов и умеет их безвозвратно удалять.

Дополнительно вход защищён от перебора: после `ADMIN_LOGIN_MAX_ATTEMPTS` неудач
с одного IP форма блокируется на `ADMIN_LOGIN_LOCKOUT_SECONDS` секунд.

**Потерян телефон с аутентификатором.** Резервных кодов нет намеренно — их
пришлось бы где-то хранить, и они стали бы вторым паролем. Восстановление
только через сервер: очистить `ADMIN_TOTP_SECRET` в `.env`, перезапустить
сервис (вход снова по одному паролю), сгенерировать новый секрет, подключить
аутентификатор, вернуть секрет в `.env`. Доступ по SSH к серверу и так означает
полный контроль над сервисом, так что новой дыры это не открывает.

**Держите один воркер uvicorn.** Счётчики неудачных входов и защита от
повторного использования TOTP-кода хранятся в памяти процесса. При нескольких
воркерах перебор пароля разъедется по процессам, а лимит вырастет во столько
же раз. Сейчас systemd-юнит запускает один процесс — так и оставить. Понадобится
масштабирование — переносить счётчики в общее хранилище (та же SQLite или Redis).

## Что пишется в лог сервиса

Полноценного аудит-лога в БД нет — он потребовал бы новой таблицы, а схема общая
с главным сервисом. Ключевые события уходят в журнал systemd:

```bash
sudo journalctl -u favorit-admin | grep -E 'Вход|Удаление'
```

Пишутся: успешный вход (с IP и с отметкой, был ли второй фактор), неудачный вход
с причиной, срабатывание блокировки по перебору, удаление данных пользователя
по 152-ФЗ. Последнее логируется **до** самого удаления: после него ни
пользователя, ни его событий в базе не остаётся.

Ограничение: `journalctl` ротируется и не ищется из интерфейса админки. Если
понадобится полноценный журнал с фильтрами — это отдельная таблица и отдельное
согласование.

## Контроль качества и рейтинг менеджеров

Два независимых потока по оценкам клиентов.

**Низкая оценка (0-7)** — недовольный клиент. Воркер ставит задачу на отдел
контроля качества в течение 10 минут. В админке строка подсвечена, видно
номер задачи и ответственного менеджера.

**Лучшие оценки (9-10)** копятся и раз в месяц превращаются в рейтинг
менеджеров. Первого числа отчёт за прошлый месяц уходит тремя задачами:
руководителям контроля качества и сопровождения и генеральному директору.

**8 — нейтральная**, не влияет ни на что. Семёрка отнесена к низким по
решению бизнеса: клиент, поставивший 7, чем-то недоволен, и разбирать это
лучше до того, как он уйдёт.

Границы настраиваются (`QC_DETRACTOR_MAX`, `QC_PROMOTER_MIN`) и **все
подписи в интерфейсе строятся из них** — «0-7», «8», «9-10» нигде не
зашиты в разметку. Меняете порог в `.env` — подписи следуют за ним.

### Как считается рейтинг

**Итог = количество лучших оценок минус количество низких.** Считаем штуки,
а не сумму баллов.

Сумма оценок сюда не годится: она вознаграждает объём. Менеджер с десятком
клиентов набрал бы больше того, у кого клиентов трое, даже работая заметно
хуже. При счёте штук менеджер с 5 лучшими и 4 низкими (итог +1) закономерно
проигрывает тому, у кого 2 лучших и ни одной низкой (итог +2).

Лидером может стать только менеджер, получивший **хотя бы одну оценку 9-10**:
месяц без похвал — не повод объявлять лидера, даже если у остальных итог
хуже. «Не определён» в рейтинге показан, но лидером не становится — это
дырка в данных, а не сотрудник.

### Что нужно настроить

```bash
BITRIX_WEBHOOK_URL=https://<портал>.bitrix24.ru/rest/<id>/<токен>/
BITRIX_QC_HEAD_ID=0        # руководитель отдела контроля качества
BITRIX_SUPPORT_HEAD_ID=0   # руководитель отдела сопровождения
BITRIX_CEO_ID=0            # генеральный директор
```

Вебхуку нужны права `crm` (чтение — искать ответственного за клиента) и
`task` (создание задач). Пока переменные пусты, сервис работает, но задачи
не создаются — в разделе «Контроль качества» админка прямо пишет, чего не
хватает.

### Воркер

```bash
sudo cp scripts/favorit-nps.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now favorit-nps.timer
systemctl list-timers favorit-nps.timer     # проверить расписание
```

Вручную:

```bash
.venv/bin/python scripts/nps_worker.py                      # обычный прогон
.venv/bin/python scripts/nps_worker.py --dry-run            # только состояние
.venv/bin/python scripts/nps_worker.py --report 2026-07 --force  # переотправить
```

Воркер идемпотентен: повторный запуск не создаёт вторых задач и не шлёт отчёт
дважды. Поэтому таймер можно дёргать сколь угодно часто, а упавший прогон
чинится следующим.

### Ограничение: нужна правка основного backend

**Оценки ниже 8 сейчас не сохраняются вообще** — их отбрасывает `favorit-app`
до записи в базу. Пока эта правка не выкачена, раздел работает только по
промоутерам: рейтинг считается, а низких оценок физически нет.

Что менять — в [docs/patch-favorit-app-nps.md](docs/patch-favorit-app-nps.md).

## Стадии банкротства

На дашборде: средний срок дела целиком, сколько клиентов сейчас на каждой
стадии и средний срок прохождения каждой стадии. Данные из воронки Битрикса
«БФЛ. Сопровождение» (`CATEGORY_ID=15`).

Считать это запросами на лету нельзя — сотни обращений и секунды ожидания при
каждом открытии админки. Поэтому локальный снимок: воркер обновляет его раз
в час, страница читает готовые цифры.

### Методика

Цифры попадают в отчёты руководству, поэтому методика зафиксирована и
подписана прямо под таблицей в интерфейсе.

- **Завершение дела — стадия «Долг списан»**, а не закрытие сделки: сделка
  может висеть открытой ещё долго после списания.
- **Средние — только по завершённым.** Прохождения стадии, которые ещё идут,
  и дела, не дошедшие до списания, в среднее не входят: их срок не истёк, и
  они занизили бы результат. Отказы и провалы исключены по той же причине.
- **Медиана рядом со средним.** Одно дело на два года сдвигает среднее так,
  что оно перестаёт описывать типичный случай.
- **Меньше трёх завершённых прохождений — пишем «мало данных»**, а не цифру.
  Среднее по двум делам это не статистика.
- **«Дольше всех» важнее среднего**: застрявшее дело видно сразу, ожидание
  дольше полугода подсвечено.

### Классификация стадий

Не все стадии воронки — этапы работы, и смешивать их в один средний срок
значит скрывать, где дело реально стоит. Разложены так (настраивается):

| Роль | Стадии | Как учитывается |
|---|---|---|
| Работа | Договор заключен, Сбор документов, Переданы на подачу, Поданы, Заявление принято, Реструктуризация, Реализация | в воронке и средних сроках |
| Ожидание | Оставлено без движения, Заседание отложено, Пауза | помечены «ожидание, не работа» |
| Завершение | Долг списан, Успешно реализовано | не считаются «в работе» |
| Провал | Условный отказ, Отказ от работы, Сделка провалена | вне среднего срока дела |
| Служебные | тех.этап, Клиенты от Гараджи | скрыты: не этап, а признак |

**Реструктуризация и Реализация — взаимоисключающие процедуры.** Клиент
проходит одну из них, поэтому они помечены «одна из двух» и не складываются
в общий путь.

## Отдел сопровождения: отказы и зависшие дела

Раздел на вкладке «Качество». Три вещи.

### Отказы по менеджерам

Рядом с каждым менеджером — сколько дел всего, сколько отказов и **доля
отказов**. Доля важнее числа: у менеджера с 50 делами и 10 отказами это 20 %,
а у менеджера с 10 делами и 5 отказами — 50 %. По абсолютным числам первый
выглядит вдвое хуже, хотя работает вдвое лучше. Таблица отсортирована по
доле, а не по количеству.

Отдельная колонка — **«из-за менеджера»**: только отказы с причиной «Не
устроил менеджер». Цена, обстоятельства клиента и наш собственный отказ по
критериям к его работе не относятся, и вешать их на менеджера значит получить
не метрику качества, а генератор обид.

**Никто не скрывается.** В таблице все, кто встречается в сделках: уволенные
и роботы помечены значками, но остаются на виду — их дела никуда не делись,
и прятать их значит терять часть картины. Кого исключить из рассмотрения,
решает тот, кто смотрит: у одного вопрос про отдел сопровождения, у другого —
почему на роботе висят дела.

Фильтры над таблицей: поиск по фамилии и должности, должность из списка
реальных значений, статус (действующие или уволенные), тип учётной записи,
порог доли отказов и минимальное число дел. Отбор мгновенный, итоги под
таблицей считаются по отобранному, а не по всей компании.

### Причина рядом с каждым отказом

Хранится не только причина, но и **кто её назвал**. Если отказы влияют на
премию, а причину указывает сам менеджер, «клиент передумал» вытеснит всё
остальное за месяц. Поэтому источник виден в таблице: «со слов клиента»,
«контроль качества», «со слов менеджера».

По каждому новому отказу без причины воркер ставит задачу отделу контроля
качества — выяснить у клиента. Механика та же, что для низких оценок.

Если в Битриксе уже ведётся поле с причиной отказа, укажите его код
в `BITRIX_REFUSAL_REASON_FIELD` — значение подтянется с пометкой
«из карточки Битрикса». Заполненную вручную причину оно не затирает.

### Дела в зоне риска

Дело, стоящее на стадии дольше нормы, — кандидат на отказ. **Норма своя
у каждой стадии**: медиана её прохождения по вашим же данным, умноженная
на `STUCK_FACTOR`. Иначе «Реализация» с её месяцами считалась бы зависшей
наравне со «Сбором документов».

Когда завершённых прохождений мало и медиане верить нельзя, берётся
`STUCK_DEFAULT_DAYS`. Нижняя граница `STUCK_MIN_DAYS` не даёт дёргать
руководителя из-за трёх дней на быстрой стадии.

По зависшему делу ставится задача руководителю отдела сопровождения —
**один раз на пару «дело + стадия»**. Дело поехало дальше и снова зависло —
это новый повод; стоять на той же стадии второй месяц поводом для второй
задачи не является.

## Жалобы клиентов

Клиент подаёт жалобу в приложении, она попадает сюда через служебный
эндпоинт основного сервиса, автоматически превращается в задачу отделу
контроля качества и видна в админке на вкладке «Качество».

**Главное ограничение — не счётчик, а дедупликация.** Пока по теме есть
открытая жалоба, вторую по той же теме подать нельзя; клиенту показывается
срок ответа по уже поданной. Это снимает саму причину дублей: человек шлёт
второе обращение, когда не понимает, что с первым. Правило взято из практики
досудебного обжалования на Госуслугах — подробно в
[docs/research-complaints.md](docs/research-complaints.md).

Числовые лимиты (3 в сутки, 10 в месяц, пауза 5 минут) — грубый
предохранитель от скрипта. Из норматива они не выведены, публичных
нормативов на объём жалоб не существует.

**Срок ответа 10 дней — требование Закона о защите прав потребителей**, а не
внутреннее пожелание: мы оказываем юруслуги физлицам, и просрочка даёт право
на неустойку. Просроченные жалобы подсвечены в админке. Внутренний дедлайн
задачи — 3 рабочих дня, с запасом на сам ответ.

Настройка и контракт для основного сервиса —
[docs/patch-favorit-app-complaints.md](docs/patch-favorit-app-complaints.md).

**Nginx не должен пускать `/admin/internal/*` снаружи:**

```nginx
location /admin/internal/ { deny all; }
```

Основной сервис ходит на `127.0.0.1:8001` напрямую, мимо nginx.

## База пишется тремя процессами

`favorit.db` пишут одновременно: этот сервис, воркер по таймеру и основной
backend. С настройками SQLite по умолчанию это ломается — журнал `delete`
блокирует базу целиком на время записи, а ждать соединение готово лишь 5
секунд.

Поэтому все подключения идут через `app/store.py`, который включает **WAL**
(читатели не блокируют писателя) и **busy_timeout 15 секунд** (соединение
ждёт освобождения вместо мгновенной ошибки). Режим WAL записывается в сам
файл базы и действует **для всех процессов, включая основной сервис** —
специально настраивать его там не нужно, менять код тоже.

Обновление стадий пишет порциями по 200 строк, а не одной транзакцией:
иначе блокировка держалась бы всё время выгрузки из Битрикса.

Рядом с базой появятся файлы `favorit.db-wal` и `favorit.db-shm` — это
нормально, они уже в `.gitignore`. **Копировать базу нужно вместе с ними**
либо после остановки сервисов, иначе копия окажется без последних записей.

### Свои таблицы

`nps_followup` (что мы узнали и сделали по каждой оценке) и
`nps_monthly_report` (факты отправки отчётов) принадлежат **только этому
сервису**. Создаются через `quality.init()`, отдельно от `db.init()` —
общую схему они не задевают, главный сервис про них не знает. Сама
`nps_scores` не изменена.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest                      # всё
pytest -m regression        # только известные дефекты
pytest -k complaints        # по имени
node tests/ui/check_ui.js   # проверки страницы отдельно, без pytest
```

Гоняются автоматически на каждый push и pull request —
`.github/workflows/tests.yml`.

### Что где

| Файл | О чём |
|---|---|
| `tests/test_regressions.py` | **Дефекты, которые уже случались.** Каждый тест — след одного бага |
| `tests/test_login.py` | Пароль, второй фактор, защита от подбора |
| `tests/test_users_collectors.py` | Поиск, фильтры, постраничный вывод |
| `tests/test_quality.py` | Градация оценок, задачи, рейтинг, месячный отчёт |
| `tests/test_complaints.py` | Правила подачи, лимиты, служебный приём |
| `tests/test_stages.py` | Синхронизация с Битриксом, воронка, сроки |
| `tests/ui/check_ui.js` | Страница админки: экранирование, вкладки, подписи |

### Про `test_regressions.py`

Это главный файл. Имена тестов — описания дефектов, в докстроке написано,
как поломка проявлялась и почему это важно. **Если такой тест покраснел,
значит вернулась известная проблема** — причину искать заново не нужно.

Проверки страницы написаны на JS не из прихоти: они разбирают настоящий
скрипт админки, подсовывают заглушки DOM и ответов сервера и смотрят, что
нарисовалось. На Python пришлось бы моделировать браузер вместо проверки
кода. Если `node` не установлен, этот тест пропускается.

Тесты не трогают боевую базу: каждому даётся своя пустая во временной папке,
а Битрикс подменяется заглушкой — сеть не дёргается.

Если добавляешь новую фичу:
1. **Новый эндпоинт** → `app/admin.py`
2. **Новый запрос в БД** → `app/db.py` (helper-функция)
3. **Новая кнопка/раздел в UI** → `app/static/admin.html`

## Что нельзя менять

`app/db.py` содержит **общую схему БД**. Функция `init()` вызывается и здесь, и в главном сервисе. Если ты добавляешь новую таблицу — согласуй с Иваном, чтобы главный сервис тоже её увидел. Изменение существующих таблиц может сломать клиентский backend.

## Деплой

Ты не деплоишь напрямую. Workflow:

1. `git checkout -b feature/название`
2. Пушишь ветку
3. Открываешь Pull Request в `main`
4. Иван ревьюит + мёржит + запускает деплой на прод

## Тестовый вход в существующую админку

Проверить как выглядит текущий UI: https://app.favorit-consult.ru/admin (пароль у Ивана).
