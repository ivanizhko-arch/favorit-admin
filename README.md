# Фаворит · Админ-панель

Изолированный сервис администратора. Отдельный от основного backend (`favorit-app`), работает на порту **8001**. Nginx маршрутизирует `https://app.favorit-consult.ru/admin/*` сюда, а `/api/*` — на главный сервис.

Читает и пишет ту же SQLite-базу `favorit.db`, что и главный сервис. Данные общие, код разделён.

## Локальная разработка

```bash
# Один раз:
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Отредактируй .env (пароль, путь к БД если нужно)

# Каждый раз:
source .venv/bin/activate
uvicorn app.main:app --reload --port 8001
```

Открой в браузере: **http://127.0.0.1:8001/admin**. Пароль — из `.env` (по умолчанию `admin123`).

## Двухфакторная аутентификация (2FA)

Вход в админку защищён TOTP-кодом (Google Authenticator, Яндекс.Ключ, 1Password).
Реализован на stdlib, без сторонних библиотек — см. `app/security.py`.

Включение:

```bash
python scripts/gen_totp.py          # выведет секрет и инструкцию
# добавить ADMIN_TOTP_SECRET=... в .env
python scripts/gen_totp.py --check <СЕКРЕТ>   # проверить до перезапуска
sudo systemctl restart favorit-admin
```

Пока `ADMIN_TOTP_SECRET` пуст, вход работает как раньше — только по паролю.
**На проде секрет должен быть заполнен**: админка управляет персональными данными
клиентов и умеет их безвозвратно удалять.

Дополнительно вход защищён от перебора: после `ADMIN_LOGIN_MAX_ATTEMPTS` неудач
с одного IP форма блокируется на `ADMIN_LOGIN_LOCKOUT_SECONDS` секунд.

**Потерян телефон с аутентификатором.** Резервных кодов нет намеренно — их
пришлось бы где-то хранить, и они стали бы вторым паролем. Восстановление
только через сервер: очистить `ADMIN_TOTP_SECRET` в `.env`, перезапустить
сервис (вход снова по одному паролю), сгенерировать новый секрет, подключить
аутентификатор, вернуть секрет в `.env`. Доступ по SSH к серверу и так означает
полный контроль над сервисом, так что новой дыры это не открывает.

**Держите один воркер uvicorn.** Счётчики неудачных входов и защита от
повторного использования TOTP-кода хранятся в памяти процесса. При нескольких
воркерах перебор пароля разъедется по процессам, а лимит вырастет во столько
же раз. Сейчас systemd-юнит запускает один процесс — так и оставить. Понадобится
масштабирование — переносить счётчики в общее хранилище (та же SQLite или Redis).

## Что пишется в лог сервиса

Полноценного аудит-лога в БД нет — он потребовал бы новой таблицы, а схема общая
с главным сервисом. Ключевые события уходят в журнал systemd:

```bash
sudo journalctl -u favorit-admin | grep -E 'Вход|Удаление'
```

Пишутся: успешный вход (с IP и с отметкой, был ли второй фактор), неудачный вход
с причиной, срабатывание блокировки по перебору, удаление данных пользователя
по 152-ФЗ. Последнее логируется **до** самого удаления: после него ни
пользователя, ни его событий в базе не остаётся.

Ограничение: `journalctl` ротируется и не ищется из интерфейса админки. Если
понадобится полноценный журнал с фильтрами — это отдельная таблица и отдельное
согласование.

## Контроль качества и рейтинг менеджеров

Два независимых потока по оценкам клиентов.

**Низкая оценка (0-6)** — недовольный клиент. Воркер ставит задачу на отдел
контроля качества в течение 10 минут. В админке строка подсвечена, видно
номер задачи и ответственного менеджера.

**Лучшие оценки (9-10)** копятся и раз в месяц превращаются в рейтинг
менеджеров. Первого числа отчёт за прошлый месяц уходит тремя задачами:
руководителям контроля качества и сопровождения и генеральному директору.

**7-8 — нейтральные**, не влияют ни на что. Границы совпадают с
классическими NPS и настраиваются (`QC_DETRACTOR_MAX`, `QC_PROMOTER_MIN`).

### Как считается рейтинг

**Итог = количество лучших оценок минус количество низких.** Считаем штуки,
а не сумму баллов.

Сумма оценок сюда не годится: она вознаграждает объём. Менеджер с десятком
клиентов набрал бы больше того, у кого клиентов трое, даже работая заметно
хуже. При счёте штук менеджер с 5 лучшими и 4 низкими (итог +1) закономерно
проигрывает тому, у кого 2 лучших и ни одной низкой (итог +2).

Лидером может стать только менеджер, получивший **хотя бы одну оценку 9-10**:
месяц без похвал — не повод объявлять лидера, даже если у остальных итог
хуже. «Не определён» в рейтинге показан, но лидером не становится — это
дырка в данных, а не сотрудник.

### Что нужно настроить

```bash
BITRIX_WEBHOOK_URL=https://<портал>.bitrix24.ru/rest/<id>/<токен>/
BITRIX_QC_HEAD_ID=0        # руководитель отдела контроля качества
BITRIX_SUPPORT_HEAD_ID=0   # руководитель отдела сопровождения
BITRIX_CEO_ID=0            # генеральный директор
```

Вебхуку нужны права `crm` (чтение — искать ответственного за клиента) и
`task` (создание задач). Пока переменные пусты, сервис работает, но задачи
не создаются — в разделе «Контроль качества» админка прямо пишет, чего не
хватает.

### Воркер

```bash
sudo cp scripts/favorit-nps.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now favorit-nps.timer
systemctl list-timers favorit-nps.timer     # проверить расписание
```

Вручную:

```bash
.venv/bin/python scripts/nps_worker.py                      # обычный прогон
.venv/bin/python scripts/nps_worker.py --dry-run            # только состояние
.venv/bin/python scripts/nps_worker.py --report 2026-07 --force  # переотправить
```

Воркер идемпотентен: повторный запуск не создаёт вторых задач и не шлёт отчёт
дважды. Поэтому таймер можно дёргать сколь угодно часто, а упавший прогон
чинится следующим.

### Ограничение: нужна правка основного backend

**Оценки ниже 8 сейчас не сохраняются вообще** — их отбрасывает `favorit-app`
до записи в базу. Пока эта правка не выкачена, раздел работает только по
промоутерам: рейтинг считается, а низких оценок физически нет.

Что менять — в [docs/patch-favorit-app-nps.md](docs/patch-favorit-app-nps.md).

### Свои таблицы

`nps_followup` (что мы узнали и сделали по каждой оценке) и
`nps_monthly_report` (факты отправки отчётов) принадлежат **только этому
сервису**. Создаются через `quality.init()`, отдельно от `db.init()` —
общую схему они не задевают, главный сервис про них не знает. Сама
`nps_scores` не изменена.

## Структура

```
app/
├── main.py          FastAPI-приложение (mount router, CORS, /health)
├── admin.py         Все /admin/api/* эндпоинты
├── db.py            Helpers по SQLite (общая схема с главным сервисом)
├── quality.py       Контроль качества, рейтинг менеджеров + свои таблицы
├── bitrix.py        Клиент Битрикс24 (вебхук): задачи, поиск ответственного
├── config.py        Настройки через pydantic-settings + .env
├── security.py      JWT, get_admin, TOTP, антиперебор логина
└── static/
    └── admin.html   Сама страница админки (HTML + inline JS)

scripts/
├── deploy.sh             Деплой на прод (запускает Иван)
├── gen_totp.py           Генерация/проверка секрета 2FA
├── nps_worker.py         Разбор оценок и месячный отчёт
├── favorit-admin.service systemd-юнит сервиса
├── favorit-nps.service   systemd-юнит воркера (oneshot)
└── favorit-nps.timer     Расписание воркера (каждые 10 минут)

docs/
└── patch-favorit-app-nps.md   Что поменять в основном backend
```

Если добавляешь новую фичу:
1. **Новый эндпоинт** → `app/admin.py`
2. **Новый запрос в БД** → `app/db.py` (helper-функция)
3. **Новая кнопка/раздел в UI** → `app/static/admin.html`

## Что нельзя менять

`app/db.py` содержит **общую схему БД**. Функция `init()` вызывается и здесь, и в главном сервисе. Если ты добавляешь новую таблицу — согласуй с Иваном, чтобы главный сервис тоже её увидел. Изменение существующих таблиц может сломать клиентский backend.

## Деплой

Ты не деплоишь напрямую. Workflow:

2. Пушишь ветку

4. Иван ревьюит + мёржит + запускает деплой на прод
